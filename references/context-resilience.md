# Устойчивость к сжатию контекста

Долгая многоэтапная задача начинается с файла состояния, а не с первого шага: он переживает сжатие
контекста, чат — нет. Файлы живут в `./swarm-report/` (обязательно в `.gitignore`).

| Файл | Назначение | Время жизни |
|---|---|---|
| `<slug>-state.md` | операционный чеклист любой длинной задачи | удалить по завершении |
| `<slug>-e2e-scenario.md` | сценарий верификации работающего приложения, источник истины для «проверено»; управляется `/acceptance` | переживает перезапуски acceptance |
| `<slug>-debug.md` | расследование бага: шаги воспроизведения, стектрейс, гипотезы, первопричина с `file:line`, план фикса; подхватывается `/acceptance` и `/create-pr` для тела PR | остаётся как audit trail |
| `<slug>-report.md` | итоговый отчёт: что сделано, результаты валидации, проблемы и откаты, статус Done / Partial / Blocked | остаётся |

```markdown
# State: <slug>
Goal: <one sentence>

## Steps
- [x] 1. <done step> → verify: <check that proved it> ✅
- [ ] 2. <next step> → verify: <check that will prove it>
```

Каждый шаг несёт `→ verify:` — конкретный сигнал, доказывающий выполнение. Расплывчатые запросы
сразу превращать в проверки: «добавить валидацию» → «тест на невалидный ввод проходит»; «починить
баг» → «регрессионный тест, воспроизводящий его, проходит».

## Правило перечитывания

Перед каждым действием, зависящим от предыдущего состояния, — сначала прочитать файл. Завершённые
шаги (`[x]`) не переделываются, возобновлять с первого `[ ]`. Помечать `[x]` только после
верификации, никогда спекулятивно. Откат шага — отредактировать файл: файл истина, чат нет.

При `/compact` и завершении сессии активный state-файл и есть точка восстановления.

## Живой статус в интерфейсе

Durable-файл переживает сжатие, но не показывает прогресс в интерфейсе, пока идёт работа. При
исполнении многошаговой задачи вести параллельно живой список задач харнеса: один пункт на шаг,
ровно один в работе, перевод в завершённые сразу по верификации шага.

Роли разделены: **durable-файл — источник истины и точка восстановления**, живой список —
эфемерная проекция, гибнущая вместе с сессией. Поэтому список пересидируется из файла при
возобновлении, а не наоборот. Шаг завершён, когда согласны оба.

Скиллы-авторы (`write-plan` пишет `tasks.md` и делает hand-off) список не ведут — его ведёт
исполнитель.
