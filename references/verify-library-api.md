# Верификация library API до написания кода

Обязательно перед Edit/Write кода с внешней библиотекой. Memorized signatures источником не
являются; код проекта — только используемый срез API и может быть legacy.

**Два канала параллельно.** Артефакт разрешённой версии (сорсы, декларации, заголовки) отвечает,
что API существует; вендорская документация — как им пользоваться сейчас. Только первый даёт
компилируемый, но устаревший код; только второй — сигнатуру, которой в этой версии нет.
Инструменты каждого канала — `~/.claude/references/external-sources.md`.

**Оба канала обязательны, когда библиотека в активной эволюции:** частые minor с breaking changes,
переписанный слой API, недавняя major. Признак — реальная история релизов, а не память о ней.

## Reference implementations

Перед нетривиальной фичей искать референс-код проактивно, наравне с доками: реальный код часто
сильнее доков в роли «как соединить X» — wiring, DI, слои. Для API truth он остаётся supporting.

- **Vendor-endorsed** — сэмпл или reference-приложение самого вендора фреймворка → T1/T2.
- **Domain-OSS** той же предметной сферы → T3, никогда не единственный источник.

Ссылаться на `owner/repo` и путь, не копировать код в правила. Версия стека в референсе далеко от
версии проекта — понизить вес: риск deprecated path.

## Быстро меняющийся декларативный UI

Мало проверить, какой API существует: нужно ещё, как сейчас рекомендуется собирать экран, иначе
получается компилирующийся, но устаревший код. Официальные reference-приложения здесь важнее доков.

Три вещи, которые легко взять неверно и которые дешевле проверить, чем угадать:

- **Где issue-трекер.** У части фреймворков он не в том GitHub-репозитории, куда ведёт интуиция.
- **Чем задаётся версия.** BOM, umbrella-артефакт или собственная версия у каждого модуля — от этого
  зависит, какую версию вообще проверять.
- **Форк против upstream.** Мультиплатформенный форк библиотеки имеет собственную нумерацию и может
  отставать от upstream: версию каждого артефакта проверять отдельно.
