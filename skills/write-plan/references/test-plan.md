# Тест-план — метод и формат

Разобрать фичу по её спецификации, дизайну или реализации и выдать структурированный,
приоритизированный тест-план markdown-документом. Здесь ничего не исполняется: выход — документ,
который подхватит device-блок `/acceptance`, агент `manual-tester` либо QA-инженер-человек.

Это был отдельный скилл `generate-test-plan` до 2026-07-30. Теперь это фаза `write-plan`: тест-план
решается вместе с планом реализации, который он проверяет, а не отдельной церемонией.

## Выход

Каждый тест-план сохраняется в репозиторий:

```
docs/testplans/<slug>-test-plan.md
```

Каталог `docs/testplans/` создать, если его нет. **Слаг — это слаг плана**, тот же, что разрешает
`docs/plans/<slug>/`; второй никогда не выводить. `/acceptance` монтирует тест-план по точному
совпадению слага, поэтому разошедшийся слаг молча ломает передачу.

### Расписка

Выпустить также расписку в `swarm-report/<slug>-test-plan.md`, чтобы `multiexpert-review` и
`/acceptance` могли монтировать артефакт через гейтинг по расписке. Источник истины — постоянный файл
в `docs/testplans/`, расписка это метаданные плюс указатель.

Полная YAML-схема, конвенции полей (`status`, `review_verdict`, `review_warnings` / `review_blockers`,
`phase_coverage`, `platform`, `created` / `updated`) и правила монтирования уже существующих файлов —
в [`test-plan-receipt.md`](test-plan-receipt.md).

## Обнаружение входов

Источниками могут быть текстовая спека (PRD, AC, user story), макет Figma либо существующий код — и
чаще всего их сочетание. Сверять их между собой; расхождения спеки и кода выносить находкой,
поведение, выведенное только из кода, помечать `[inferred from code]`.

**Frontmatter спеки.** Если источник — файл с YAML-frontmatter, содержащим список `platform:`,
скопировать его дословно в поле `platform:` расписки (канонические значения:
`android | ios | web | desktop | backend-jvm | backend-node | cli | library | generic`, те же, что у
`write-spec`). Иначе оставить `platform:` в расписке пустым — приёмка откатится на свою эвристику
определения типа проекта.

**Макет Figma.** Через инструменты Figma MCP извлечь состояния экранов, интерактивные элементы, потоки
навигации и платформенные варианты.

### Детектор не-UI — когда брать облегчённый шаблон

Триггер не-UI тест-плана — `~/.claude/rules/qa-and-testing.md`. Когда он срабатывает, выбросить
разделы, идущие от макета (колонки Steps и Expected Result), и делать TC, чьё поведение полностью
выражается через Given/When/Then, сосредоточившись на валидации ввода, переходах состояний и путях
ошибок. Смешанные фичи (бэкенд плюс тонкий UI) по умолчанию идут в стандартном формате.

Сработал детектор — отметить это в разделе Findings постоянного файла:
`**Lightweight template applied** — UI-поверхности не обнаружено; TC используют только Given/When/Then.`

## Формат тест-плана

У каждого тест-плана одинаковая верхнеуровневая раскладка: YAML-frontmatter с `type: test-plan` и
`slug`, таблица метаданных в шапке, затем `Findings`, `Risk Areas`, `Test Cases`,
`Edge Cases & Negative Scenarios`, `Coverage Matrix` и `Suggested Automation Candidates`. Каждый блок
`TC-[N]` сам является таблицей со строками `Priority`, `Tier`, `Preconditions`, `Steps`,
`Expected Result` и `Source`.

Существуют два варианта:

- **Стандартный формат** — по умолчанию, с полными колонками Steps и Expected Result.
- **Облегчённый формат (не-UI фичи)** — когда сработал детектор не-UI, блоки TC схлопывают Steps и
  Expected Result в одну строку `Scenario (Given/When/Then)`. Остальные разделы не меняются.

Когда у фичи две и более фазы (например поэтапная раскатка) и тест-кейсы группируются по фазам,
разбить раздел `## Test Cases` на подразделы `### Phase N (T-i..T-j) — <метка>`, оставаясь в одном
постоянном файле на фичу. Тогда `phase_coverage` в расписке перечисляет присутствующие метки фаз.

Полные стандартный и облегчённый шаблоны дословно, разобранный пример разбиения по фазам и правила,
когда какой вариант применяется, — в [`test-plan-templates.md`](test-plan-templates.md).

## Определения полей

### Type

Каждый тест-кейс объявляет явный `Type` плюс однострочный `Type rationale` (см.
`test-plan-templates.md`). Это поле читают потребители ниже по потоку — coverage-аудит `/acceptance`,
профиль test-plan в `multiexpert-review`, инженерные агенты, пишущие сами тесты, — и оно не
опционально.

| Type | Область | Брать, когда |
|---|---|---|
| `unit` | один класс или функция с подменёнными соседями | чистая логика, преобразование, валидатор, mapper, парсер, арифметика держателя состояния |
| `integration` | несколько классов плюс реальные или in-memory зависимости | репозиторий с БД, сервис с тестовым API, конвейер данных, взаимодействие нескольких классов |
| `ui-instrumentation` | один UI-компонент внутри своего фреймворка (Compose UI test, XCUITest на одном экране, ViewInspector) | действие пользователя на одном экране или компоненте с проверкой видимого состояния |
| `ui-scenario` | работающее приложение, управляемое MCP-раннером устройства или браузера, перезапускаемый сценарий | пользовательский путь через несколько экранов, критичный кроссплатформенный флоу |
| `screenshot` | сравнение визуального рендера (Paparazzi, swift-snapshot-testing) | визуальная точность является частью контракта — дополняет, но никогда не единственное покрытие |
| `e2e` | приложение целиком, сквозняком | критичный для релиза путь, который нельзя разбить на меньшие типы; число таких держать малым |

#### Эвристика выбора

На каждый критерий приёмки брать **наименьшую область, ловящую реальный отказ этого AC**. Подниматься
выше только когда нужно. При сомнении предпочитать более дешёвый тип.

| Форма AC | Type |
|---|---|
| Преобразование значения, чистое вычисление | `unit` |
| Взаимодействие компонентов с реальными или поддельными соседями | `integration` |
| Действие на одном экране с видимым изменением состояния | `ui-instrumentation` |
| Путь через несколько экранов | `ui-scenario` |
| Критичный для релиза путь плюс важна визуальная точность | `screenshot` (дополнительно) и/или `e2e` |
| Критичный сквозной поток, который нельзя разбить | `e2e` |

Эта эвристика — канонический ориентир при выборе типа TC.

### Priority

Рамка приоритетов — `~/.claude/rules/qa-and-testing.md`.

### Tier

| Tier | Значение | Ориентир |
|---|---|---|
| **Smoke** | Живо ли оно? | минимальный набор, подтверждающий, что фича работает вообще (не более 3–5 тестов) |
| **Feature** | Работает ли правильно? | тщательное покрытие поведения фичи |
| **Regression** | Не сломали ли что-то? | защита от поломки существующей функциональности |

### Source

| Тип источника | Формат | Пример |
|---|---|---|
| Раздел спеки | `Spec §[раздел]` | `Spec §3.2 — Login flow` |
| Фрейм Figma | `Figma: [имя фрейма]` | `Figma: Login / Error State` |
| Путь в коде | путь со строкой в бэктиках | `src/auth/LoginViewModel.kt:87` |
| Выведено | `[inferred from code]` | поведение выведено из кода без опоры на спеку |

### Non-functional / Instrumentation (обязателен для user-facing и prod-bound)

Каждый план заканчивается разделом `## Non-functional / Instrumentation`, объявляющим наблюдаемость
**до** реализации, а не после первого инцидента. Обязателен, когда спека или задача помечены
`user-facing` либо `prod-bound`, а также когда фича трогает горячий путь наблюдаемости: сетевые
вызовы, платежи, фоновые задания, авторизацию, миграции данных.

`N/A: <причина>` в одну строку допустим для внутреннего инструментария и для чистых рефакторингов без
изменения наблюдаемого поведения. Сам заголовок не удалять никогда.

Раздел покрывает пять подразделов — Log events, Metrics, Traces, Alerts, Dashboards (полный шаблон в
[`test-plan-templates.md`](test-plan-templates.md#non-functional--instrumentation)). Конвенции
именования и стек (OpenTelemetry, Prometheus, StatsD, вендорские) берутся из `CLAUDE.md` проекта и
переиспользуются; свой стек здесь не предписывается. Конвенции в проекте нет — задать один вопрос и
записать ответ.

Этот раздел потребляют дальше:

- профиль test-plan в `multiexpert-review` проверяет, что раздел заполнен либо несёт явный
  `N/A: <причина>`;
- `/acceptance` проверяет на работающем приложении, что объявленные события и метрики действительно
  испускаются, когда исполняется проверяемое поведение.

## Правила

- Нумеровать тест-кейсы подряд: TC-1, TC-2, TC-3 … (`manual-tester` присваивает свои идентификаторы в
  рамках сессии уже при исполнении).
- Каждый тест-кейс утверждает ровно одно — проверки с несколькими исходами разбивать.
- Выведенное поведение помечать `[inferred from code]`.
- Целиться в 15–30 тест-кейсов на среднюю фичу; каждый TC обязан заслужить своё место.
