# Write Spec

Превращает идею фичи в исчерпывающую спецификацию, которая служит контрактом для автономной
реализации. После утверждения агент-реализатор идёт сквозняком и обращается к пользователю только на
критических блокерах.

**Роль:** бизнес-аналитик и тимлид в одном лице. Докапывается до настоящей потребности за запросом,
оценивает подходы, рекомендует лучший для этого контекста.

**Принципы:**

1. **Запрос пользователя — вход, а не мандат.** Предложенное решение («добавь ретраи с backoff») —
   один из кандидатов, а не ответ. Исследовать независимо и рекомендовать оптимальный подход, прямо
   сказав, права ли идея пользователя, права ли частично или проигрывает альтернативе.
2. **За поверхностным запросом прячется глубокая сложность.** «Хочу кнопку вывода средств»
   подразумевает платёжную инфраструктуру, комплаенс, интеграции с банками, антифрод. Показать
   айсберг до того, как писать спеку.
3. **Внимание пользователя дорого.** Исследовать всё, на что можно ответить без вопроса. Каждый
   вопрос идёт с рекомендованным ответом, который можно принять или переопределить.

## Фаза 0: разобрать вход

### 0.1 Отделить потребность от предложенного решения

Извлечь:

- **Бизнес-потребность** — лежащая в основе проблема или цель, часто неявная.
- **Предложенное решение** — то, что пользователь сказал буквально: один кандидат, не ответ.
- **Известные ограничения** — платформа, библиотеки, «без новых зависимостей», срок.
- **Предполагаемый контекст** — что пользователь знает и чего он мог не учесть.

Когда потребность и предложенное решение расходятся («хочу кнопку вывода» → потребность:
пользователи забирают заработанное), признать оба. Спека закрывает бизнес-потребность лучшим
доступным решением.

Сгенерировать kebab-case слаг (`offline-mode`, `push-notifications`).

Артефакты:

- Спека: `docs/specs/YYYY-MM-DD-<slug>.md` — версионируется, постоянная.
- Состояние: `./swarm-report/spec-<slug>-state.md` — операционное, удаляется по завершении.

### 0.2 Скрытая сложность и глубина scope

Две проверки до исследования.

**Скрытая сложность** — отметить в файле состояния, когда запрос называет элемент UI, а настоящая
работа в бэкенде; когда он подразумевает внешние сервисы, деньги, юридическую сторону или комплаенс;
когда он меняет флоу, от которого зависят другие фичи; когда в нём доменный жаргон, способный
означать разный объём работ. Показать айсберг рано — одно из самых ценных, что делает этот скилл.
Фича очевидно огромна (месяцы, несколько команд) — сказать это сразу и задать один вопрос про объём.

**Неоднозначность глубины scope** — когда одна и та же формулировка означает радикально разный объём
(«пуш-уведомления» — локальные алерты против полной интеграции FCM/APNs), задать ОДИН вопрос с
вариантами от минимального до полного и рекомендацией по контексту проекта. Пропускать, если объём
понятен. Триггеры: внешние сервисы, интеграция нескольких систем, возможности уровня ОС.

**Гейт понимания домена (сначала research).** Собственная фаза исследования этого скилла (фаза 1)
исходит из того, что *направление уже выбрано*: она детализирует понятую область — кодовую базу,
конкретные API, уже решённые интеграции, — но НЕ обнаруживает, *как это вообще должно работать* и
какие подходы существуют. Если **как** до сих пор неизвестно (подходы, реализуемость, внешние
регуляции ещё не поняты — например, «вывод денег» до того, как разобрана механика переводов,
комплаенс и интеграция с банком), — STOP и сначала отдельный скилл `research`, а к спеке вернуться,
когда понимание собрано. Спека **фиксирует** понятое в контракт, инструментом первичного обнаружения
она не является. Конвейер: `research` (понять) → `write-spec` (зафиксировать контрактом) → план →
реализация.

### Выбор исследовательских треков

Не запускать всё подряд. Треки активируются там, где дают полезный сигнал:

| Признак | Треки |
|---|---|
| Существующая функциональность продукта | Кодовая база + бизнес-аналитик |
| Новый модуль, пересечение слоёв, архитектурное изменение | Кодовая база + архитектура |
| Внешний API, протокол, алгоритм, незнакомый домен | Веб-исследование |
| Расплывчатая идея, непонятное влияние на пользователя | Бизнес-аналитик |
| Вопрос по библиотеке, версиям или зависимости | Веб-исследование плюс канал реестра зависимостей |
| Простое изменение в одном модуле | Только кодовая база |

**Если в проекте есть бизнес-документы и документы требований** (`docs/`, спеки в `*.md`, связанные
issue), прочитать их **до** запуска агентов: они часто отвечают на вопросы заранее.

**Дефолт при неуверенности:** кодовая база плюс бизнес-аналитик, остальное добавлять по мере того,
как находки вскрывают пробелы.

## Фаза 1: исследование

### 1.1 Запустить консорциум

Запустить всех выбранных агентов **одним сообщением**, параллельно. Каждый работает независимо.

Доступные треки:

- **Кодовая база (`Explore`)** — включать всегда. Существующий код, паттерны, зависимости, границы
  модулей, TODO, тестовая инфраструктура.
- **`architecture-expert`** — новый модуль, смена направления зависимостей, новые абстракции,
  несколько слоёв.
- **Веб-исследование** — внешние протоколы, нетривиальные алгоритмы, интеграция со сторонним,
  незнакомый домен.
- **`business-analyst`** — влияние на пользователя, непонятный объём, расплывчатая идея.
- **Критическая оценка** — пользователь предложил конкретный технический подход либо в кодовой базе
  есть устоявшиеся паттерны, которые могли устареть. Выдаёт три варианта подхода: радикальный,
  классический, консервативный.
- **Цепочка зависимостей** — внешние сервисы, возможности уровня ОС, инфраструктура, фаза настройки.

Промпты по агентам брать из [`references/research-prompts.md`](references/research-prompts.md)
дословно.

### 1.2 Файл состояния

Создать `./swarm-report/spec-<slug>-state.md` до запуска агентов. Стандартные поля по глобальному
шаблону файла состояния плюс разделы этого скилла:

- **Input** — цель, мотивация, известные ограничения.
- **Research Tracks** — чеклист запущенных и пропущенных треков, с причиной пропуска.
- **Findings** — наполняется по мере завершения агентов.
- **Interview Log** — наполняется в фазе 2.

Обновлять по мере завершения каждого агента.

## Фаза 2: интервью

**Входной контракт:** исследование завершено, находки лежат в файле состояния, пользователю ещё не
задано ни одного вопроса, кроме необязательного про глубину scope.

**Цикл раундов** — характерный паттерн именно этого скилла:

1. Синтезировать находки против чеклиста фичи: разрешения, поведение платформы, предусловия,
   состояния ошибок, безопасность, производительность, обратная совместимость.
2. Разложить оставшееся: **уже известно** (пропустить), **предлагаемые дефолты** (предложить на
   подтверждение), **настоящие пробелы** (спросить).
3. Если критическая оценка выдала три варианта подхода, а подход ещё не выбран, показать их
   **первыми** и дождаться выбора: он формирует все последующие вопросы.
4. Задать открытые вопросы в принятом формате, к каждому рекомендованный ответ и альтернативы.
   Ждать.
5. Записать ответы в файл состояния. Проверить, не появились ли новые пробелы. Повторить.

**Выход:** открытых пробелов не осталось и подход выбран → фаза 3. Упёрлись в предел раундов —
оставшееся становится неблокирующими открытыми вопросами в спеке, блокеры помечаются для ревью в
фазе 4.

**Разбиение крупной фичи на фазы.** Если фича распадается на несколько независимых фаз, предложить
поэтапный подход. Согласился — специфицировать только фазу 1, остальное уходит в «Future Phases».

Чеклист фичи, подача вариантов подхода, формат вопроса, скрипт раунда и шаблон фазирования — в
[`references/interview-rounds.md`](references/interview-rounds.md).

## Фаза 3: написать черновик спеки

Писать спеку так, будто читатель — агент-реализатор без всякого дополнительного контекста. Ничего
нельзя оставить на догадку. Каждое требование проверяемо. Каждое решение явно и с обоснованием.

Следовать каноническому markdown-шаблону: YAML frontmatter с `type`/`slug`/`date`/`status` плюс
необязательные `platform`/`surfaces`/`risk_areas`/`non_functional`/`acceptance_criteria_ids`/`design`,
которые управляют приёмкой ниже по потоку и фазой тест-плана в `write-plan`; затем разделы тела:
Context and Motivation, Acceptance Criteria (со стабильными идентификаторами `AC-N`), Prerequisites,
Affected Modules and Files, Technical Approach, Technical Constraints, Decisions Made, Out of Scope,
Open Questions, Future Phases.

Полный шаблон — поля frontmatter, заголовки разделов, форма таблиц и встроенные инструкции — в
[`references/spec-template.md`](references/spec-template.md): скопировать его в черновик дословно и
заполнить каждый плейсхолдер.

## Фаза 4: цикл ревью

### 4.0 Проход по TODO до ревью

До запуска любого рецензента прогрепать все исходные документы, на которых стоит спека, на
незакрытые пункты:

```bash
grep -rniE 'TODO|FIXME|verify|needs investigation|to be confirmed|TBD|XXX' \
  --exclude='<имя-файла-спеки>' \
  <каталоги-исходных-документов>
```

Вместо `<имя-файла-спеки>` подставить реальное имя (`2026-05-27-offline-mode.md`), чтобы сама спека
никогда не сканировалась. Вместо `<каталоги-исходных-документов>` — реальные каталоги исходных
документов этого репозитория (`docs/design/ docs/research/`). **Не** добавлять `2>/dev/null`: если
каталога нет, grep напечатает ошибку, и это именно то, что нужно — отсутствующий каталог под
`2>/dev/null` молча даёт пустой вывод, неотличимый от «находок нет».

По каждому совпадению:

- **Закрыто в спеке** — спека явно это адресует (AC, решение или абзац технического подхода).
  Действий нет.
- **Вне scope** — раздел `## Out of Scope` явно это перечисляет, при желании с владельцем или
  указанием, куда отложено. Действий нет.
- **Ни то ни другое** — пробел. Либо закрыть по месту, либо внести в Out of Scope до продолжения.
  **Не пропускать.**

Зачем это существует: списки TODO в baseline-, research- и review-документах кодируют вопросы,
которые авторы источников уже знали как неотвеченные. Спека, их игнорирующая, стоит на заведомо
неполном основании. Реальный режим отказа: в документе визуального соответствия написано «отрисовка
drop-shadow TBD», спека это не адресует, и пилотные разработчики упираются в пробел на шестой неделе
реализации.

Проверка механическая — автоматизировать её. Не доверять ощущению «кажется, всё покрыли».

### 4.1 Показать черновик пользователю

Полную спеку в чат **не** вставлять: артефакт — файл спеки, а чат нужен для навигации. Вместо этого
компактная сводка:

- заголовок спеки и цель одним предложением;
- три-пять ключевых критериев приёмки, по идентификатору `AC-N` и короткой подписи;
- открытые вопросы, оставшиеся нерешёнными.

Если открытые вопросы есть, задать ровно ОДИН из них сейчас. После ответа вернуться за следующим,
если он остался.

### 4.2 Самопроверка, пока пользователь читает

Пока пользователь смотрит черновик, прогнать самопроверку:

- каждый критерий приёмки объективно проверяем (не «должно ощущаться быстрым»);
- каждый затронутый модуль перечислен с типом изменения;
- ни одно решение не оставлено на усмотрение агента-реализатора;
- out of scope явен, ничего не подразумевается случайно;
- блокирующих открытых вопросов не осталось;
- **все TODO из исходных документов по §4.0 закрыты** — перегрепать после правок, ожидать ноль
  необработанных совпадений;
- **у каждого пользовательского взаимодействия** (жест, событие, системный триггер) есть полная
  механическая спецификация: для любого перетаскивания, тапа, долгого нажатия, свайпа, жеста «назад»,
  системного события — условия срабатывания, предусловие по состоянию, визуальная обратная связь,
  правило hit-testing и разрешения координат, момент фиксации, испускаемые колбэки, режимы отказа.
  Наполовину описанные взаимодействия («пользователь может перетащить виджет» без якоря, hit-test и
  математики зоны сброса) — главный источник переделок после утверждения.

Найденные самим пробелы закрыть.

### 4.3 Прогнать multiexpert-review (профиль spec)

Запустить `multiexpert-review` с явной подсказкой профиля:

```
multiexpert-review --profile=spec
---
<полное содержимое спеки + исходная цель фичи>
```

Подсказка — защита в глубину: у инлайновых вызовов нет frontmatter, по которому классифицирует
детектор, и префикс замыкает определение детерминированно
([`references/profile-hint-rationale.md`](references/profile-hint-rationale.md)).

Черновик пока в памяти и ещё не сохранён в `docs/specs/`, поэтому движок классифицирует источник как
`conversation` и использует `inline-revise` для правок при FAIL: итерации цикла правок идут инлайново.

Панель профиля `spec` (`business-analyst`, `architecture-expert` плюс условные) подтверждения не
требует — движок объявляет состав строкой и запускает. Другой состав — `--experts=<список>`.

Профиль spec (панель: `business-analyst` плюс `architecture-expert`) проверяет фальсифицируемость AC,
реалистичность предусловий, явность Out of Scope, наличие обоснований у решений, полноту списка
затронутых модулей, разделение блокирующих и неблокирующих открытых вопросов, детальность
технического подхода.

**Панель рецензентов не сокращать.** Включать ВСЕХ сработавших рецензентов, которые установлены: если
сработал `optional_if` профиля (`security-expert` на PII, auth и шифровании, `performance-expert` на
SLA, задержках и бюджетах, `ux-expert` на accessibility и UI), движок включает их при наличии и
пропускает при отсутствии — про пропущенного из-за отсутствия сказать вслух, а не терять перспективу
молча. Пропускать сработавшего рецензента на основании «эта область уже разобрана в прошлом ревью
исходного исследования» — ложная экономия: каждый цикл ревьюит другой артефакт (спека и research —
разные тексты, даже когда пересекаются по теме), и здесь важен взгляд рецензента именно на контракт
уровня спеки. Цена включения — две-пять минут на дополнительного агента. Цена пропуска — пробелы,
всплывающие уже после утверждения; типичные жертвы это детали визуальных взаимодействий, бюджеты
производительности и флоу accessibility.

| Вердикт | Действие |
|---|---|
| PASS | Продолжать |
| Minor | Починить по месту, отметить изменения |
| CONDITIONAL и противоречия | Вынести пользователю, разрешить |
| FAIL | Движок ведёт цикл правок; повторять до PASS/CONDITIONAL либо до эскалации пользователю |

Эскалация (предел `multiexpert-review` исчерпан, всё ещё FAIL) — не финал: пользователь разрешает
блокер, черновик правится по его указанию, а затем **обязательно** возобновляется
`multiexpert-review --profile=spec --max-cycles=6` тем же составом, продолжая счётчик цикла — правка
по директиве пользователя открывает право на повторный прогон, а не заменяет его (протокол —
`~/.claude/skills/multiexpert-review/SKILL.md`'s «После эскалации: возобновление»). Фаза 4.6 переводит
спеку в `approved` только на фактический PASS/CONDITIONAL этого (возможно, возобновлённого) прогона;
единственное исключение — явный оверрайд пользователя своими словами, тогда `approved` не
проставляется, вместо этого — открытый вопрос `[unreviewed]` с дословной причиной.

### 4.4 Раунд обсуждения после ревью

Когда самопроверка и multiexpert-review завершены, а любой из них поднял вопросы или проблемы,
показать их пользователю на финальный раунд обсуждения. Это может вернуть в формат вопросов-ответов
фазы 2, чтобы закрыть остаток пробелов.

### 4.5 Проход «прогулка реализатора» (враждебный)

Рецензенты находят проблемы. **Реализаторы находят недостающее.** Это разные режимы отказа:
рецензент, читающий «AC-DRAG-1: тень перетаскивания рисуется из getWidgetIcon», видит выполненный AC;
реализатор, которому сказали «построй это», немедленно спрашивает — где тень относительно пальца? как
понять, какой слот является целью сброса? Мышление рецензента такого вопроса не порождает, мышление
реализатора порождает.

Запустить **одного** general-purpose агента на sonnet с брифом:

> Ты изображаешь инженера-реализатора для `<путь к спеке>`. Не ревьюй спеку — попробуй ей
> *воспользоваться*. Возьми самое сложное пользовательское взаимодействие в спеке (перетаскивание,
> сложный жест, многошаговый флоу) и мысленно просимулируй его реализацию от начала до конца: от
> триггера пользователя → переходы состояний → визуальные обновления → колбэки → очистка. Каждый раз,
> когда тебе пришлось бы *угадывать* деталь или задавать уточняющий вопрос, — выпиши это. Вывод:
> список пунктов вида «пришлось бы угадать X, потому что спека не задаёт Y». Не более 15 пунктов.

По каждому пункту:

- **Закрывается тривиально** (уточнение в одну строку) → починить по месту и идти дальше.
- **Требует решения по дизайну** → вынести пользователю вопросом в формате фазы 2.
- **Уже задано, агент не заметил** → действий нет, упомянуть в обсуждении.

Цена: три-пять минут одного агента. Избегаемая цена: правки после утверждения, когда пилотные
разработчики упрутся в пробел неделями позже.

Пропускать только для небольшого, хорошо очерченного изменения без сложных взаимодействий.

### 4.6 Утверждение

Когда пользователь удовлетворён и вопросов не осталось, перевести статус спеки из `draft` в
`approved` и переходить к сохранению. **Условие «вопросов не осталось» включает фактический
PASS/CONDITIONAL последнего прогона `multiexpert-review`** — обсуждение находок с пользователем
(4.4) и его согласие с направлением фикса не эквивалентны пройденному ревью; если правки вносились
после эскалации по 4.3, `approved` ставится только после возобновлённого прогона движка, а не сразу
по итогам разговора с пользователем.

## Фаза 5: сохранить

Сохранить утверждённую спеку в `docs/specs/YYYY-MM-DD-<slug>.md`, перевести `status` во frontmatter
из `draft` в `approved`, убрать файл состояния, подтвердить одним предложением с предложением
следующего шага (`/write-plan`, который заодно решит, нужен ли изменению тест-план, либо

## Красные флаги и условия STOP

- **Фундаментальное противоречие** — критерии приёмки взаимоисключающи либо ограничение делает фичу
  невозможной. Вынести конфликт наружу, обходной путь не выдумывать.
- **Нет критичного доступа** — фиче нужны системы, API или credentials, которых нет. Перечислить
  недостающее и остановиться.
- **Scope действительно безграничен** — после одной попытки его очертить он всё ещё слишком велик
  для спеки. Предложить поэтапный подход и дождаться согласования.
- **Решение требует продуктовых полномочий** — выбор имеет бизнесовые, юридические или брендовые
  последствия, которые команда не может принять в одиночку. Пометить блокирующим открытым вопросом.
