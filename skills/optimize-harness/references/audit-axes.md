# Оси аудита

По каждой оси: сигнал, чем измерить, типовые находки. Команды даны от корня харнеса.

---

## 1. Контекстный бюджет always-on

**Сигнал.** Инструкции (`CLAUDE.md` + безусловные `rules/`) выросли настолько, что перед первым
сообщением пользователя уже израсходовано заметное окно.

```bash
scripts/measure-harness.sh <корень> -v
```

**Типовые находки.** Один файл держит треть бюджета (у процессных правил это почти всегда правило
про тестирование или про воркфлоу). Правило, дублирующее содержимое скилла, который его же и
исполняет. Правило, состоящее из общеизвестных практик.

**Оценка выигрыша** — в байтах и в доле от бюджета инструкций. Ориентир: файл дороже ~5 000 b почти
наверняка содержит деталь, нужную не всегда.

---

## 2. Дублирование между слоями

**Сигнал.** Одно и то же требование живёт в `CLAUDE.md`, в правиле и в скилле. Каждый экземпляр
платит токенами, а расходиться они начинают при первой же правке одного из них.

```bash
grep -rn --include='*.md' -iE 'force|hooks|зависимост|baseline|пирамид' CLAUDE.md rules/ | sort
```

Отдельный вид дублирования, который легко не заметить: **правило, повторяющее сам харнес**.
Системный промпт Claude Code уже задаёт поведение — не писать преамбул, сообщать о блокерах, не
сужать scope молча, спрашивать подтверждение на необратимое. Правило про то же самое платит дважды
и ничего не добавляет.

**Что делать.** Оставить одну формулировку в файле, который темой владеет, остальные снять. Если
нужен указатель — короткая ссылка, не пересказ.

## 3. Кандидаты на прогрессивное раскрытие

**Сигнал.** Текст нужен в один конкретный момент (при выборе уровня верификации, при добавлении
зависимости, при создании worktree), а платится каждой сессией.

**Как отличить костяк от детали.** Костяк отвечает на «что должно произойти и когда» — он должен
сработать без запроса. Деталь отвечает на «как именно это устроено» — её можно прочитать по
указателю в момент срабатывания. Таблица состава уровней — деталь. «L5 обязателен для бампов
версий» — костяк.

**Куда выносить** — в каталог, про который спайк сказал `NOT LOADED`. Механика деления и ловушки —
`splitting.md`.

## 4. Маршрутизация model и effort

**Сигнал.** У агента не задан `model:`, и он молча наследует модель сессии. Промах ходит в обе
стороны: на дорогой сессии механический агент оплачивается по верхней ставке, на sonnet-сессии
думающий агент тихо деградирует. Читать вместе с текущим `"model"` в `settings.json` — без него
колонка `<нет>` ни о чём не говорит.

```bash
for f in agents/*.md; do
  printf '%-34s model=%-10s effort=%s\n' "$(basename "$f")" \
    "$(grep -m1 '^model:' "$f" | cut -d' ' -f2-)" \
    "$(grep -m1 '^effort:' "$f" | cut -d' ' -f2-)"
done
```

**Типовые находки.** Поисковый или lookup-агент без `model: haiku`. Ревьюер, которому нужен высокий
effort, но он его не получает. **`effort:` вместе с моделью Haiku — ошибка вызова**, у Haiku этого
рычага нет; это конкретный сбой, а не стилистика.

**Осторожно.** Понижение модели у агента, который принимает решения (разрешает конфликт по смыслу,
диагностирует причину, выбирает между вариантами), экономит копейки и стоит качества. Ошибка в
сторону дешёвой модели видна сразу, в сторону дорогой — невидима и оплачивается всегда.

## 5. Шум permissions

**Сигнал.** Сессия часто останавливается на подтверждении read-only команды.

```bash
python3 -c "import json;s=json.load(open('settings.json'))['permissions'];print({k:len(v) for k,v in s.items()})"
```

**Типовые находки.** Read-only команды в `ask` вместо `allow`. Правила, покрытые более общим и
потому мёртвые. Домены `WebFetch`, накопленные под давно закрытую задачу.

**Не трогать `deny`.** Это единственный слой, который стоит между агентом и необратимым действием;
«лишним» он выглядит ровно до первого срабатывания. Сбор allowlist из транскриптов закрывает
отдельный скилл `fewer-permission-prompts` — при большой находке уместнее сослаться на него.

## 6. Hooks

**Сигнал.** Старт сессии заметно задерживается, либо hook пишет в артефакт, который никто не читает.

```bash
python3 -c "import json;h=json.load(open('settings.json')).get('hooks',{});
print({k:sum(len(g.get('hooks',[])) for g in v) for k,v in h.items()})"
for f in hooks/*.sh; do bash -n "$f" && echo "syntax OK $f" || echo "СЛОМАН $f"; done
```

**Типовые находки.** Hook, который когда-то собирал телеметрию, а сейчас его нет в `settings.json`,
хотя артефакт остался, — или наоборот, зарегистрирован, а скрипта нет. Отсутствующий `timeout` у
сетевой команды на `SessionStart`. Дорогой hook, который можно перевести на фон.

**Проверка hook — только реальный запуск.** Валидный shell и корректный JSON в `settings.json` не
доказывают, что он срабатывает.

## 7. MCP-серверы и плагины

**Сигнал.** Подключено больше, чем используется. Каждый сервер добавляет описания инструментов в
контекст; часть харнесов откладывает схемы и держит только имена, часть — нет, и это стоит проверить
на месте, а не предполагать.

```bash
python3 -c "import json;s=json.load(open('settings.json'));print(list(s.get('mcpServers',{})));print(s.get('enabledPlugins'))"
```

**Типовые находки.** Сервер под задачу, закрытую полгода назад. Плагин, скиллы которого ни разу не
вызывались. Сервер, требующий интерактивной авторизации, — он отваливается в headless и cron-прогонах,
и это стоит знать до, а не во время.

## 8. Инвентарь агентов и скиллов

**Сигнал.** Два агента с перекрывающимся назначением; описание, которое не помещается в бюджет
листинга; ссылка на несуществующий файл.

```bash
grep -rhoE '`?references/[a-z0-9-]+\.md`?' skills agents | tr -d '`' | sort -u   # затем проверить существование
grep -rn --include='*.md' -oE '\[\[[a-z0-9-]+\]\]' rules references agents skills | sort -u
```

**Типовые находки.** Описания скиллов с длинными перечислениями триггеров: **листинг режется молча
при превышении бюджета**, поэтому такое описание платит токенами и не доезжает до маршрутизации.
Ссылки `[[slug]]` на файл, который переехал. Скилл, полностью поглощённый другим.

**Осторожно с описаниями агентов.** В них короткие отрицательные границы («не для отладки багов —
`debugging-expert`») выглядят водой, но именно они не дают промахнуться маршрутизации. Сокращать их
имеет смысл, только если видно конкретное повторение, а не ради метрики.
