# RULEBOOK, маркеры, инвентарь пробелов

RULEBOOK — единственный источник решений о трансляции для миграции. Каждый исполнитель, транслирующий
файл, читает один и тот же RULEBOOK и применяет его без собственных суждений; ничто не решается для
каждого файла отдельно, если это можно решить один раз, в правиле.

## Построение RULEBOOK

Начинать его в фазе 1, до веера. Засеять из таксономии фазы 0 и из первого прохода по горстке
репрезентативных файлов — достаточно, чтобы назвать повторяющиеся формы, а не составить исчерпывающий
каталог заранее. Каждая запись задаёт исходный паттерн, целевой паттерн, в который он превращается,
обоснование в одну строку и именованные исключения. Запись без обоснования — это предпочтение, а не
правило, и она не переживёт первого спора на ревью.

Фаза 2 существует ровно для того, чтобы сломать RULEBOOK намеренно: прогнать его по нескольким
специально выбранным неудобным файлам до того, как доверять ему всё дерево. Правило, видевшее только
лёгкий случай, — догадка в форме правила.

Скелет для дословного копирования при старте новой миграции — `rulebook-template.md`.

## Чинить цикл, а не код

Систематический дефект, найденный при трансляции или на ревью, — это дефект правила, а не того
единственного файла, где он всплыл. Фикс такой: поправить правило и перепрогнать каждое место, которого
оно касается, — но никогда не патчить отдельный файл по месту и идти дальше. Патч, обошедший правило,
невидим для всех остальных мест с тем же дефектом, и следующий проход молча вернёт дефект туда, где
файл снова тронут.

Это та же дисциплина, что чинить баг в первопричине, а не в первом симптоме, применённая к трансляции
вместо логики: исправляется артефакт-правило, а транслированные файлы — его выход и порождаются из
него заново.

## Только для чтения внутри цикла

RULEBOOK **только для чтения внутри цикла**, и в особенности внутри пачки. Исполнитель, транслирующий
файл N, не правит правило, которое управляет файлом N, — даже когда с его места правило выглядит
неверным. Поправки предлагаются, ревьюятся и применяются **только между пачками**: после того как
текущая пачка закончена, и до того как началась следующая. Рассуждение простое: смена правила посреди
пачки означает, что файлы с 1 по k в той же пачке транслированы против правила, которого больше нет, и
никто не скажет, какие именно это файлы, не передиффив всю пачку.

Находки, которые изменили бы правило, уходят обратно в RULEBOOK к следующей границе пачки, а не вбок,
в тот файл, который их вскрыл.

## Маркеры

Три маркера фиксируют работу, которую правило пока не разрешает механически. Каждый ставится ровно в
том месте, к которому относится, и каждый зарабатывает строку в инвентаре пробелов.

- `TODO(port)` — для места ещё нет правила; сопоставление должен решить человек или более сильная
  роль, прежде чем место можно закрыть.
- `BUG(port)` — известно, что механическая трансляция здесь меняет поведение, и фикс не сводится к
  механическому правилу: нужна точечная правка.
- `PERF(port)` — трансляция сохраняет поведение, но меняет характеристики производительности
  настолько, что нужно осознанное решение, а не умолчание.

Маркер без соответствующей строки в инвентаре пробелов — утечка: место помечено в коде, но невидимо
тому, кто отслеживает остаток. Пачка не считается завершённой, пока хоть один введённый ею маркер
остаётся без строки.

## Инвентарь пробелов

По строке на каждое место, которое RULEBOOK не транслирует механически. Инвентарь — единственное
место, отвечающее на вопрос «что осталось» без грепа маркеров по всему дереву: он дополняется по мере
того, как места всплывают при трансляции и на ревью, и строка убирается только тогда, когда её маркер
снят и соответствующий код его больше не несёт.

Скелет для дословного копирования — `inventory-template.md`.
