# QA и тестирование

Каждая задача, изменяющая код, определяет стратегию тестирования на этапе планирования: какие
уровни пирамиды и какие инструменты. «Просто», «быстрый фикс», «очевидно» причиной пропуска не
являются.

## Пирамида верификации

| Уровень | Название | Описание |
|---|---|---|
| L0 | Build | затронутая часть (приложение/модуль, не всегда весь репо) компилируется |
| L1a | Статический анализ | lint, типы, аудит зависимостей — машинные проверки, всегда |
| L1b | Экспертное агентное ревью | суждение о смысле изменения, а не о его форме: корректность, безопасность, производительность, архитектура — набор экспертов по профилю изменения |
| L2 | Изолированные тесты | поведение единиц без реального окружения — быстро, на подменённых зависимостях |
| L3 | Интеграционные тесты | поведение в реальном окружении, автоматизированно — на поднятом рантайме и настоящих зависимостях |
| L4 | E2E-тесты | сквозной сценарий целиком |
| L5 | Ручная верификация | наблюдение работающей системы человеком или агентом |

Нумерация уровней сквозная и стабильная: `L1` в любой другой записи (`rules/task-types.md`,
план, `implement-plan`) означает **оба** подуровня. L1a и L1b разделены потому, что это
разные по природе проверки — машинная и суждение: первая либо проходит, либо нет, вторая даёт
находки с severity и требует цикла fix. Пропуск L1b — отслеживаемое исключение с причиной,
не дефолт: зелёный lint про корректность не говорит.

L1b — **агентное** ревью, и человеческое ревью в PR его не замещает: они ловят разное и
происходят в разные моменты. Ревьюер в PR видит уже собранный результат и судит о замысле;
L1b проходит до PR, по свежему диффу, и обязан закрыть свои находки циклом fix, а не оставить
их комментариями. Обратное тоже верно — пройденный L1b не отменяет ревью людьми там, где оно
принято.

### Уровень задаёт глубину, проект задаёт состав

Определения выше универсальны и не зависят от стека и вида артефакта. **Чем именно закрывается
уровень — решает проект**: инструменты, команды, пороги. Дефолт — не «пропустить уровень», а
**вывести состав из стека самостоятельно, применить и записать в отчёте, что было использовано**.
Отсутствие конкретизации в проекте не делает уровень неприменимым.

Порядок определения состава уровня:

1. Явная конкретизация проекта — `CLAUDE.md` проекта, план задачи, доменная матрица
   (пример: `skills/migrate-code/references/verification-matrix.md` для миграций).
2. Вывод из стека: обнаруженные раннеры, конфиги линтеров, доступное окружение для интеграционных
   прогонов, существующая структура тестов.
3. Вывода не хватает — назвать это явно и оформить отслеживаемым исключением с причиной, никогда
   молча.

Один и тот же уровень наполняется по-разному, и это норма, а не исключение: L0 для кода — «модуль
компилируется», для конфигурации — «YAML/JSON парсится», для схемы — «схема валидна». L5 для
приложения — работающее приложение, для конфигурации — реальный запуск: hook сработал,
permission-правило отвергло вызов, свежая сессия без warnings. Для конфигурации L5 не опционален и
чтением диффа не заменяется — это тот же верификатор, что требует `CLAUDE.md`: «валидный JSON» и
«выглядит правильно» проверкой не являются.

**Специфичная проверка не получает собственного номера** — она встаёт на уровень, соответствующий
её механике исполнения. Структурный анализ MD-скилла (обязательные секции, живые ссылки на
`references/`, длина описания в бюджете листинга) — это L1a: машинная проверка формы.

**Производительность — не отдельный уровень, а другой критерий на существующем.** Бенчмарк без
реального окружения исполняется как L2, инструментальный замер в нём — как L3. Отличается вердикт:
обычный тест бинарен, perf даёт число, которое ничего не значит без baseline. Поэтому у perf-задачи
L0 и baseline обязательны, а «прошло» без дельты — не результат ([[task-types]]).

**Новый guard или гейт (L1a) считается доказанным только отвергнутым push'ем.** Регистрации задачи в
агрегатной (`check`, `verify`, CI-джоб) недостаточно: спровоцировать нарушение и увидеть отказ
фактического pre-push hook или CI.

**L5 обязателен для:** бампов версий библиотек (даже patch), tech/framework-миграций, изменений
infra-слоя (network, storage, auth, DI), любой задачи «не должно влиять на поведение».

**L5 закрывать автономно.** Поднять окружение и управлять системой самому доступными в проекте
инструментами; доступность проверять эмпирически, а не объявлять L5 нереализуемым из теории.
Привлекать пользователя — крайняя мера: недостижимые credentials, закрытый контур, поведение только
на реальном железе.

**Окружение L5 — эксклюзивный ресурс.** Два агента, работающих с одним экземпляром, перезаписывают
друг другу состояние. Сериализовать либо давать каждому своё; при нескольких экземплярах адресовать
целевой явно.

**Верификатор L5 — код завершения или проверка наблюдаемого состояния, а не текст лога:** лог
объясняет почему, но решением не является. Сужать вывод до попадания в контекст, большой — в файл.
Секреты редактировать до передачи в контекст: читаемые логи подчиняются тому же правилу, что и
пишемые ([[logging]]).

## Gate покрытия public API

Изменённый публичный символ должен проверяться тестом. Публичный — видимый за пределами своего
модуля по правилам языка.

**Тест не нужен:** чистые носители данных без логики; builder DSL без логики; реэкспорт.

**Нет изменения поведения — нет нового теста.** Перемещение, переименование, переупаковка, правка
импортов изменением символа не считаются. Gate срабатывает на изменение поведения или сигнатуры.

**Сопоставление по приоритету:** (1) файл символа ↔ одноимённый тестовый файл по конвенции языка;
(2) имя символа встречается в тестовом файле того же модуля; (3) явная аннотация покрытия.
Ничего не нашлось — написать тест или пометить тривиальным.

## Прочее

- **Одноразовые верификационные тесты.** Для подтверждения миграции допустимо написать тест,
  прогнать и удалить — это леса, принадлежащие автору. Чужое покрытие удалять нельзя.
- **Не-UI поверхность** (нет макетов, нет визуального слоя) — покрывать только валидацию ввода,
  переходы состояний и пути ошибок; вопросы раскладки, accessibility и visual-regression пропускать.
- **Автор чинит сломанные тесты в том же PR.** Отключение теста запрещено без ссылки на
  отслеживаемую задачу в самой аннотации отключения — например
  `@Ignore("flaky under CI parallelism — JIRA-1234")`. Никаких «merge red».
- **Блокироваться и спрашивать там, где догадка будет неверной:** конфигурация сборки и запуска
  тестов, если она неоднозначна; владелец изменённых файлов в монорепо.

## Источник истины верификации

Обязательный результат планирования — определяет «готово» и служит контрактом для `/acceptance`.

| Тип | Когда | Артефакт |
|---|---|---|
| Задача / требования | явные AC или чёткая задача | заметки плана, список AC |
| Спецификация | слишком велико для головы, нужны отслеживаемые AC | `/write-spec` → `docs/specs/<slug>-spec.md` |
| Тест-план | структурированные исполняемые случаи | `/generate-test-plan` → `docs/testplans/<slug>-test-plan.md` |
| Дизайн-макеты | визуальные AC для UI | Figma в спецификации `design.figma`, скриншоты |
| Debug-артефакт | багфиксы — контракт это шаги воспроизведения | `swarm-report/<slug>-debug.md` |
| Поведенческий baseline | миграция, «не должно влиять на поведение» | захватить до изменений — [[task-types]] |

Источника нет и создать нереально — задокументировать в плане предполагаемое поведение, причину
отсутствия и используемый proxy. `/acceptance` блокируется на ненайденном источнике; обоснованный
proxy это не обход гейта.
