# QA и тестирование

## Стратегия обязательна

Каждая задача, изменяющая код, определяет стратегию тестирования на этапе планирования: какие
уровни пирамиды и какие инструменты. Пропуск — только с весомой причиной («код не изменяется,
только markdown»); «просто», «быстрый фикс», «очевидно» не принимаются.

### Пирамида верификации

Уровни последовательны: каждый требует пройденного предыдущего, переход выше обосновывается.

| Уровень | Название | Описание |
|---|---|---|
| L0 | Build | затронутая часть (приложение/модуль, не всегда весь репо) компилируется |
| L1 | Статический анализ | lint, типы, code review, аудит зависимостей — всегда |
| L2 | Unit-тесты | быстрые, без устройства, чистая логика |
| L3 | UI-тесты | автоматизированные, нужен эмулятор/устройство |
| L4 | E2E-тесты | полный автоматизированный флоу |
| L5 | Ручная верификация | mobile MCP / `manual-tester` на работающем приложении |

**Новый guard или гейт (L1) считается доказанным только отвергнутым push'ем.** Регистрации задачи
в агрегатной (`check`, `verify`, CI-джоб) недостаточно: спровоцировать нарушение и увидеть отказ
фактического pre-push hook или CI. Сверять реальные точки входа гейта, а не факт подключения.

**L5 обязателен для:** бампов версий библиотек (даже patch), tech/framework-миграций, изменений
infra-слоя (network, storage, auth, DI), любой задачи «не должно влиять на поведение».

**L5 закрывать автономно.** Управлять приложением через mobile MCP (`mcp__mobile__*`), иначе
`adb`/`android` CLI ([[android-cli]]) или `manual-tester`. Эмулятор/симулятор по умолчанию;
физическое устройство — только когда нужно реальное железо (biometric HAL, камера, NFC, GPS,
sensor fusion). Доступность проверять эмпирически (`adb devices -l`, `emulator -list-avds`,
`xcrun simctl list`), не объявлять L5 нереализуемым из теории; нужный AVD не установлен, но
получается легко — установить. Собрать и установить APK самому. Привлекать пользователя — крайняя
мера: недостижимые credentials, backend за VPN, поведение только на физическом железе.

**Устройство под L5 — эксклюзивный ресурс.** Два device-трогающих агента на одном устройстве
перезаписывают друг другу APK. Сериализовать либо давать каждому своё: `emulator -avd <name>
-read-only` поднимает вторую копию, не трогая состояние основного. При нескольких устройствах —
все adb-команды с явным `-s <serial>`.

### Стоимость L5

Приёмка — самая дорогая фаза, и дорога она способом управления устройством, а не моделью. Порядок
выбора инструмента через mobile MCP — от дешёвого к дорогому:

| Что нужно | Чем брать | Цена |
|---|---|---|
| Есть ли элемент, что на экране | `ui(action:'tree', format:'semantic')` | ~60 токенов |
| Только интерактивные элементы | `ui(action:'tree', compact:true)` | ~100 |
| Найти конкретный элемент | `ui(action:'find')` | ~150 |
| Быстрая визуальная сверка | `screen(action:'capture', preset:'low')` | ~1500 |
| Полный скриншот | `screen(action:'capture')` | ~3000 |

- Дерево вместо скриншота по умолчанию. Скриншот — когда проверяется именно визуальное: раскладка,
  letterbox, контраст, соответствие макету.
- `flow(action:'batch')` для последовательностей — каждый тап отдельным turn'ом главный источник
  кружения.
- Input-действия уже возвращают diff интерфейса; скриншот после каждого тапа — антипаттерн.
- `screen(diff:true)` после действия. Дерево и скриншот вместе не запрашивать.

Скриншоты обязательны при сверке с макетом, регрессиях раскладки и доказательстве «до/после».

### Захват логов в L5

- **Верификатор детерминированный, а не текст лога.** pass/fail определяет код завершения теста,
  результат сборки или `assert_visible`. Лог объясняет почему, но сам по себе решением не является.
- **Фильтровать и сужать scope до попадания в контекст.** Уровень ≥ ERROR; scope по package/PID на
  Android (`--pid=$(adb shell pidof -s PKG)`, `get_logs(level="E", package=…)`), по `subsystem` на
  iOS (`simctl log show --predicate 'subsystem=="<bundleId>"'`); ограничивать объём (`-m N`, tail);
  большой вывод — в файл, агент читает путь. Паттерны крешей: Android `FATAL EXCEPTION`,
  `AndroidRuntime: FATAL`, ANR, unhandled NPE; iOS `fault`/`error`.
- **Редактировать секреты до передачи в контекст.** Читаемые логи подчиняются тому же правилу «что
  не идёт в лог», что и пишемые ([[logging]]): не передавать сырые `.env`, `curl -v`, заголовки
  `Authorization`; маскировать `Bearer .*`, `*_TOKEN`, `*_KEY`, PII.

### Одноразовые верификационные тесты

Для подтверждения миграции или разового поведения допустимо написать тест, прогнать и удалить.
Это леса, принадлежащие автору, — в отличие от чужого покрытия, которое удалять нельзя.

## Gate покрытия public API

Изменённый публичный символ должен проверяться тестом. Публичный = Kotlin без `internal`/`private`,
Swift `public`/`open`, TS `export`.

**Тест не нужен:** чистые носители данных (`data class`, Swift `struct` только с хранимыми
свойствами, TS interfaces, enums, type aliases); builder DSL без логики; реэкспорт проверенного
символа.

**Нет изменения поведения — нет нового теста.** Перемещение или переименование файла,
переупаковка, правка импортов изменением символа не считаются: существующие тесты и зелёная сборка
уже покрывают. Gate срабатывает на изменение поведения или сигнатуры, не на смену местоположения.

**Сопоставление по приоритету:** (1) `Foo.kt` ↔ `FooTest.kt` / `FooTests.swift` / `Foo.test.ts`;
(2) имя символа встречается в тестовом файле того же модуля; (3) аннотация `@CoveredBy("...")`.
Ничего не нашлось — написать тест или пометить тривиальным до прохождения `/check`.

## Приоритеты тестов

**P0** критичное для релиза (краш, потеря данных, безопасность, платежи, auth — падение блокирует
релиз); **P1** по одному тесту на каждый AC-N из спецификации, названному по этому AC; **P2** happy
path, один успешный флоу на интерфейс; **P3** границы, пустые значения, locale/timezone, большой
ввод, race conditions. Косметическое и исследовательское в формальные планы не входит — только
исследовательское QA через `manual-tester`.

## Облегчённый тест-план для не-UI

При выполнении всех трёх условий — нет макетов, поверхность API/library/CLI, нет ревью `ux-expert`
в scope — покрывать только валидацию ввода (типы, диапазоны, некорректные данные), переходы
состояний и пути ошибок. Viewport, accessibility и visual-regression пропускать.

## Автор чинит сломанные тесты в том же прогоне

Кто сломал существующие тесты — чинит их в том же PR. `@Ignore` / `xit` / `t.Skip` запрещены без
ссылки на отслеживаемую задачу в аннотации: `@Ignore("flaky on iOS 17 — JIRA-1234")`. Никаких
«merge red» и «починим позже».

## Инфраструктуру определяет проект

Runner, имена задач и команды читать из инструкций проекта (`<repo>/CLAUDE.md`) или конфига сборки.
Проект не указывает — определять по маркерным файлам в корне (`build.gradle*`, `Package.swift`,
`package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `Makefile`). Блокироваться и спрашивать
там, где догадка будет неверной: схема и назначение Xcode, флаги Python runner, владелец
изменённых файлов в монорепо.

## Источник истины верификации

Обязательный результат планирования — определяет «готово» и служит контрактом для `/acceptance`.

| Тип | Когда | Артефакт |
|---|---|---|
| Задача / требования | явные AC или чёткая задача | заметки плана, список AC |
| Спецификация | слишком велико для головы, нужны отслеживаемые AC | `/write-spec` → `docs/specs/<slug>-spec.md` |
| Тест-план | структурированные исполняемые случаи | `/generate-test-plan` → `docs/testplans/<slug>-test-plan.md` |
| Дизайн-макеты | визуальные AC для UI | Figma в спецификации `design.figma`, скриншоты |
| Debug-артефакт | багфиксы — контракт это шаги воспроизведения | `swarm-report/<slug>-debug.md` |
| Поведенческий baseline | миграция, «не должно влиять на поведение» | захватить до изменений — [[task-types]] |

Источника нет и создать нереально — задокументировать в плане предполагаемое поведение, причину
отсутствия и используемый proxy. `/acceptance` блокируется на ненайденном источнике; обоснованный
proxy это не обход гейта.
