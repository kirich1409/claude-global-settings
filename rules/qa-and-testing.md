# QA и тестирование

Каждая задача, изменяющая код, определяет стратегию тестирования на этапе планирования: какие
уровни пирамиды и какие инструменты. «Просто», «быстрый фикс», «очевидно» причиной пропуска не
являются.

## Пирамида верификации

| Уровень | Название | Описание |
|---|---|---|
| L0 | Build | затронутая часть (приложение/модуль, не всегда весь репо) компилируется |
| L1a | Статический анализ | lint, типы, аудит зависимостей — машинные проверки, всегда |
| L1b | Экспертное агентное ревью | суждение о смысле изменения: корректность, безопасность, производительность, архитектура — набор экспертов по профилю изменения |
| L2 | Изолированные тесты | поведение единиц на подменённых зависимостях |
| L3 | Интеграционные тесты | поведение на поднятом рантайме и настоящих зависимостях |
| L4 | E2E-тесты | сквозной сценарий целиком |
| L5 | Ручная верификация | наблюдение работающей системы человеком или агентом |

Нумерация сквозная и стабильная: `L1` в любой другой записи означает **оба** подуровня. Уровень
задаёт глубину, а состав уровня выводится из проекта — дефолт не «пропустить уровень», а вывести
состав из стека и записать в отчёте, чем закрыл.

**L5 обязателен для:** бампов версий библиотек (даже patch), tech/framework-миграций, изменений
infra-слоя (network, storage, auth, DI), любой задачи «не должно влиять на поведение», любой правки
конфигурации. Для конфигурации L5 — реальный запуск, а не чтение диффа.

**Изменённый публичный символ должен проверяться тестом** — когда изменились поведение или
сигнатура; перемещение и переименование не считаются.

Детали — `~/.claude/references/verification-pyramid.md`: состав уровней по стеку, исполнение L5, gate
покрытия public API, gate тестируемости, источник истины верификации. Читать перед `/acceptance`,
при выборе стратегии тестирования и при споре «нужен ли здесь тест».
