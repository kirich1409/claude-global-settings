# Kotlin

Проектные соглашения и то, что модель упускает по умолчанию. Общий идиоматичный Kotlin (null
safety, именование, организация кода) здесь не документируется — доверять модели и официальным
Kotlin coding conventions.

## Видимость — минимальная по умолчанию

Приоритет: `private` (внутри файла или класса) → `internal` (между файлами модуля) → `public`
(намеренная часть внешнего API). Дефолтная `public` «потому что компилируется» недопустима.
Сомневаешься между `internal` и `public` — брать `internal`: расширить позже тривиально, сузить —
ломающее изменение. В проекте есть другое устоявшееся соглашение — следовать проекту.

Привязка к структуре модулей:

- Feature и implementation модули (`internal/` пакеты, `feature/.../internal/`, всё не в `api/`) →
  `internal` по умолчанию, `private` когда символ не покидает свой файл.
- Public API модули (`api/`, контракты в `:protocol/`, shared infra) → `public` только для
  предназначенного другим модулям; внутренние хелперы всё равно `internal`/`private`.
- Классы, sealed-иерархии, конструкторы, члены `companion object` — то же правило. Класс
  инстанцируется только через фабрику или DI → конструктор `internal`/`private`.
- Ключевое слово `public` явно не писать — это дефолт, шум без сигнала.
- В `.kts` то же самое: top-level хелперы в convention plugins и `build.gradle.kts` — `private`,
  если используются только в этом скрипте.

## Коллекции — операторы вместо `for`

Для операций над коллекцией, `Sequence`, `Map` или `Flow` предпочитать стандартный оператор
императивному циклу: имя оператора документирует намерение, тело `for` с `if`/`add`/`continue` его
скрывает.

`for` уместен, когда выполняется хотя бы одно:

- ранний `return` из объемлющей функции по телу цикла (из `forEach` без `return@label` не выйти);
- несколько побочных эффектов за итерацию, не компонующихся в одно преобразование;
- индексный доступ и доступ к соседям, где `zipWithNext`/`windowed` менее понятны, чем
  `for (i in indices)`;
- горячий путь с измеримыми аллокациями промежуточных коллекций — сначала пробовать `asSequence()`,
  переходить к `for` только после профилирования.

Больше трёх операторов подряд или башня `let` — пересмотреть, но не переходить к `for` механически.

## Named arguments

Именовать аргумент, когда выполняется хотя бы одно:

- примитивный тип (`Boolean`, `Int`, `String`), смысл которого неочевиден в месте вызова;
- несколько параметров одного типа — именовать каждый из них;
- одиночный булев литерал — всегда, даже если аргумент единственный.

```kotlin
// Плохо
createUser("Alice", "alice@example.com", "password123")
setRetry(true, 3)

// Хорошо
createUser(name = "Alice", email = "alice@example.com", password = "password123")
setRetry(enabled = true, maxAttempts = 3)
```

Позиционный допустим для domain-типизированного аргумента, чей тип уже документирует смысл
(`show(dialog)`, `navigate(destination)`); для вызова, где имя функции делает аргумент очевидным
(`println(message)`, `delay(500)`); для операторных вызовов stdlib (`maxOf(a, b)`). Одиночный булев
литерал исключением не является никогда.

Тест: читатель, видящий только место вызова, выводит смысл каждого аргумента без угадывания.

## Пустые блоки

Вызов заканчивается пустым `{}` и существует только ради сигнатуры — удалить его целиком:
`apply {}`, `also {}`, `run {}`, `let {}`, `forEach {}`, `onEach {}`, пустой `init {}`.

Исключения:

- Пустой `catch (e: X) {}` под правило **не** подпадает: тихое поглощение исключений — отдельная
  проблема ([[task-execution]]). Либо логировать, либо убирать `try` целиком.
- Пустое тело, требуемое переопределением interface или abstract метода, — оставить с комментарием
  `// no-op: <причина>`. Без него читатель не отличит намеренное от забытого.
- Пустая лямбда как default-callback (`onClick = {}`) — оставлять, только если API требует non-null;
  иначе предпочитать nullable тип.

## Валидация value class

Обернуть примитив в `@JvmInline value class` — очевидная часть. Неочевидная: добавить
`init { require(...) }`, когда обёртка накладывает ограничение (непустая, формат, диапазон) —
модель это регулярно пропускает.

```kotlin
@JvmInline
value class Email(val value: String) {
    init { require("@" in value) { "Invalid email: $value" } }
}
```

Реального ограничения нет (непрозрачный server-generated ID) — блок `init` пропустить. Валидация не
ритуал.

## Nullable параметры

Nullable параметр на extension или top-level функции — design smell: обычно ответственность за
отсутствующее значение принадлежит уровню выше.

- Принимать non-nullable receiver и параметры: `fun String.parse()`, а не `fun String?.parse()`.
- У вызывающего nullable значение — дать перегрузку либо позволить ему использовать `?.`.
- Предпочитать перегрузки одной функции с nullable и default-параметрами, когда варианты ведут себя
  существенно по-разному.

## KMP / commonMain

- Никаких импортов `android.*`, `java.*`, `javax.*`, `dalvik.*` в `commonMain`.
- Только Kotlin stdlib и KMP-совместимые библиотеки.
- `expect`/`actual` только для platform-specific деталей реализации; бизнес-логика в `commonMain`.
- Предпочитать `kotlinx.*` вместо JVM-only: `kotlinx.datetime` вместо `java.time`,
  `kotlinx.serialization` вместо Gson/Moshi.

## Архитектура (Clean Architecture + MVI)

- UseCase — одна ответственность: один public `operator fun invoke()`.
- Интерфейсы Repository живут в domain, реализации — в data.
- Domain-модели без зависимостей от фреймворка (исключение: `kotlinx.coroutines`,
  `kotlinx.datetime`, аннотации `kotlinx.serialization`).
- Маппинг — явные функции или классы, никогда не внутри data classes.
- Не экспонировать типы data-слоя (DTO, Entity) через интерфейсы repository — маппить в
  domain-модели на границе слоя.
- `viewModelScope` и `lifecycleScope` принадлежат только Android presentation слою.
