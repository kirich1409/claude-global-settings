# Маршрутизация по типу задачи

## Gate проверки тестируемости

Тесты пишутся, когда выполняются **оба** условия:

1. Подход к покрытию понятен — существует естественная граница теста (чистая функция, API-контракт,
   известное UI-взаимодействие).
2. Усилия в разумном бюджете — тест не дороже самого изменения и не требует строить тестовую
   инфраструктуру с нуля.

Условие не выполнено — задокументировать причину в плане и продолжить без тестов для этой scope.
«Непонятно как тестировать» и «стоимость настройки непомерна» валидны, «не захотелось» нет.

Gate регулирует дискреционный scope и **не** отменяет минимум для public API: изменённый публичный
символ всё равно проверяется тестом или помечается тривиальным ([[qa-and-testing]]). Стоимость
действительно непомерна — оформить отслеживаемым исключением (`@Ignore` со ссылкой на задачу),
пробел остаётся явным.

### Снижение стоимости верификации (на этапе планирования)

- Поверхность сложно управляемая (глубоко в флоу, нужен реальный backend) → построить sample или
  sandbox-приложение, прототипировать и отлаживать там, затем переносить. Отладка сразу в реальном
  приложении — медленный путь.
- UI → screenshot-тесты и screenshot baseline; несколько эмуляторов и форм-факторов, когда
  изменение чувствительно к раскладке.
- Временные упрощения ради раннего верифицируемого прототипа допустимы, но снимаются до `/finalize`.

Цель — дешевейший путь к верифицируемому прототипу, а не откладывание тестирования. Решать это при
планировании, не в середине реализации.

## Матрица

| Тип задачи | Источник истины | Мин. пирамида | Когда писать тесты | Особое |
|---|---|---|---|---|
| Фича | спецификация, тест-план, список AC | L1–L5 (L5 при наличии UI) | после реализации; до — если AC понятны | — |
| Багфикс | `swarm-report/<slug>-debug.md`, шаги воспроизведения | L1–L2, плюс L5 при UI-регрессии | **до фикса**: сначала падающий тест | red-green |
| Tech-миграция | baseline до изменений | L1 + **L5 обязателен** | до миграции — покрыть мигрируемое поведение | сначала захватить состояние до |
| Бамп версии | baseline до изменений | L1 + **L5 обязателен** | проверить существующие, добавить при пробелах | захватить состояние до, если тестов нет |
| Рефакторинг | baseline до изменений, тесты как proxy | L1–L2, плюс L5 при UI | до рефакторинга при пробелах в покрытии | поведение 1:1 с состоянием до |
| Инфраструктура (network, storage, auth, DI) | спецификация, требования | L1 + **L5 обязателен** | после реализации | — |
| UI / дизайн | Figma, скриншоты | L1 + L3 + L5 | после реализации | визуальное сравнение с макетом |
| Производительность | benchmark baseline, числа до и после | L0 + измерение | baseline до, дельта после | измеримая дельта, никогда «ощущается быстрее» |
| Расследование | документ результатов | L1 только если написан код | N/A без изменений кода | пирамиды нет, если код не написан |

**L0 — неявный входной gate каждой строки:** затронутая часть компилируется до запуска любого L1+.
Колонка «мин. пирамида» перечисляет уровни выше L0 и никогда его не отменяет. Нет изменения кода —
нет L0.

## Watch-red-first

Там, где матрица предписывает тест до кода (багфикс, фича с понятными AC), red-green обязателен по
шагам: запустить тест и **увидеть падение**, затем писать минимальный код, затем увидеть зелёный.
Тест, который не наблюдали красным, не доказывает ничего — он мог проходить по ошибке.

Это не глобальный strict-TDD: там, где матрица предписывает тесты после реализации, правило не
применяется и удалять уже написанный код не требует.

## Baseline состояния до изменений

Снимок текущего поведения, сделанный **до любых изменений**, достаточно подробный, чтобы убедиться,
что изменённая система ведёт себя идентично.

**Что подходит:**

1. Проходящие тесты покрывают изменяемое поведение — тест-сьют и есть baseline, зелёные до = спека
   для после.
2. Покрытия нет — захватить вручную до начала: UI — скриншоты всех затронутых экранов и сессия
   `manual-tester` в `swarm-report/<slug>-baseline.md`; API — снимки форм ответов затронутых
   endpoints; производительность — текущие числа benchmark.

Покрыть мигрируемое поведение тестами до миграции закрывает и требование baseline, и `/write-tests`
за один приём.

**Проверка достаточности:** можно ли отдать этот baseline тому, кто систему не видел, чтобы он
проверил успешность миграции? Если да — достаточен.

**Baseline не является:** «должно быть нормально»; code review или статический анализ (проверяют
намерение, не рантайм); прошедшая сборка (доказывает компиляцию, не поведение).
