# Рабочий процесс

Плагины `developer-workflow` — инструменты по требованию, не принудительный pipeline.

## Шаг 0: триаж

До всего остального классифицировать входящее и выбрать маршрут. Дешёвый выход первым: цель не
навесить церемонию на мелочь, а отсечь тривиальное и развести неоднозначную середину. Идти сверху
вниз, остановиться на первой подходящей ветке.

1. **Тривиально → делать сразу.** Однострочное или механическое изменение с очевидным результатом,
   правка только доков либо конфига без логики. Мимо всех gates, без research и плана.
2. **Вопрос, а не сборка → ответить или исследовать.** Код менять не нужно — ответить; копание по
   своей кодовой базе — Explore; широкое многоисточниковое — скилл `research`.
3. **ЧТО строить не понято → сначала понять, потом зафиксировать.** Это последовательность, а не
   выбор: не понимаем, КАК это делается (подходы, ограничения, регуляции) → `research`, его выход —
   понимание, не код. Понимаем ЧТО, но нужен прочный контракт для автономной реализации →
   `/write-spec`, он фиксирует уже достигнутую ясность и не пишется поверх непонятой предметки.
   Конвейер крупной непонятой фичи: `research` → `/write-spec` → декомпозиция → план → реализация,
   где каждое звено опускается, если его вход уже есть.
4. **Слишком крупно для одной единицы → декомпозировать.** Не помещается в один план/spec/PR,
   несколько независимых deliverable, эпик — разбить и прогнать каждую часть через триаж заново.
5. **Решено и помещается → оценить сложность.** Многофайловое, рискованное или с несколькими
   путями реализации → preparation gate и `/write-plan`. Узкое, понятный путь, известный стек →
   сразу реализация.
6. **Определить тип задачи → [[task-types]].** Задаёт источник истины, минимальный уровень пирамиды
   и момент написания тестов.

## Обязательные gates

**Preparation gate — до любой реализации.** Собрать три вывода, реально собранных, а не названных:

- **Источники истины** (что означает «готово»): spec/AC, before-state baseline, скриншоты/Figma,
  debug-repro. Активно производить их — снимать скриншоты, поднимать эмулятор, фиксировать baseline
  до миграции. Чего нельзя сделать самому — спросить, назвав, что деградирует без этого. Начинать
  реализацию без источников истины нельзя. Детали: [[qa-and-testing]], [[task-types]].
- **Источники знаний** (как строить): доверенные источники T1–T4 — [[external-sources]]. Для
  нетривиальных фич проактивно искать эталонный код, не только API docs — [[verify-library-api]].
- **Тестируемость и декомпозиция:** оценить, насколько сложно верифицировать изменение, и
  предложить упрощения заранее (sample app, screenshot tests, несколько эмуляторов); разбить
  задачу, слишком большую для одного плана. Детали: [[task-types]].

Вопросы концентрировать в этой фазе; после сбора источников двигаться без лишних уточнений.
Пропускать prep — только для тривиальных случаев.

**Quality gate — `/finalize`.** Обязателен после каждой реализации с кодом, до объявления задачи
завершённой. Отвечает за то, *как написан код*: полный цикл review→fix→simplify до отсутствия
находок выше Minor или выход с ESCALATE. Разовый запуск `code-reviewer` gate не закрывает — fix и
simplify остаются невыполненными. Исключения: только доки, только конфиг без логики, однострочные
механические правки. Исключение снимает церемонию, но не верификацию: у конфига есть свой
минимальный верификатор (`validate-config`, schema, dry-run) — прогнать обязательно.

**Acceptance gate — `/acceptance`.** После `/finalize`, до продвижения PR. Верифицирует реализацию
против источника истины и запускает runtime checks, включая `manual-tester` для UI. Gates
ортогональны: `/finalize` про то, как написан код, `/acceptance` про то, что он делает. Ни один не
заменяет другой. Исключения те же.

**PR promotion gate — `/create-pr --promote`** требует явного подтверждения пользователя. Открыть
draft PR — рутина; продвижение делает PR видимым ревьюерам.

## Потоки

**Нетривиальная фича:** preparation gate → реализация на feature branch в worktree, draft PR
заранее через `/create-pr --draft` → `/check` → `/finalize` → `/acceptance` → `/create-pr --promote`
(с подтверждением) → `/drive-to-merge`. Опционально `/multiexpert-review` для высокорисковых планов.

**Багфикс:** зафиксировать шаги воспроизведения в `swarm-report/<slug>-debug.md` — это источник
истины для `/acceptance`. Написать падающий тест, затем фикс (red-green) → `/check` → `/finalize` →
`/acceptance` → PR. Регрессионный тест не опционален; исключение по feasibility gate всегда
отслеживаемое, никогда молчаливое.

**Исследовательское QA без spec:** вызвать `manual-tester` напрямую.
