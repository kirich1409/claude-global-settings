# Внешние источники

## Маршрутизация

| Источник | Для чего | Не для чего |
|---|---|---|
| Локальный код проекта | первая точка для вопросов по проекту | — |
| `ksrc` | исходники JVM/Gradle зависимостей (реальный source jar) | внутренний код проекта |
| `android docs search`/`fetch` | API truth и guides для Android/Jetpack/Compose/AGP/SDK | не-Android библиотеки |
| `~/.android/cli/skills/**/SKILL.md` | встроенные Android CLI skills: миграции, узкие области (Wear, XR, edge-to-edge, R8, Perfetto). Discovery — `android skills find <kw>` | API truth; не-Android задачи |
| Context7 | документация опубликованных библиотек, текущий API и миграции | код проекта, отладка своего кода |
| `WebSearch`/`WebFetch` | всё, что не покрыто выше | — |
| Raw README через `raw.githubusercontent.com` | последний вариант для конкретного репо | — |
| Reference implementations | «как реально собрать X»: wiring, DI, слои из живого кода — [[verify-library-api]] | API truth: это usage-срез, не спека |

`WebFetch` по rendered GitHub-страницам (`https://github.com/...`) не использовать — HTML шумный и
дорогой, брать raw.

## Каналы поиска по open-source коду

Единственный каталог этого класса; `source-researcher` и скилл `research` ссылаются сюда. Уровни
доверия берутся из [[verify-library-api]] и здесь не переопределяются.

**Режим A — внутрь известной библиотеки** (как реализовано, точная сигнатура в версии X):

| Канал | Что даёт | Tier |
|---|---|---|
| `ksrc` | сорсы подключённых зависимостей из Gradle cache, точная pinned-версия | T1 |
| `maven-mcp` + source jar | сорсы любой версии из Maven Central, в т.ч. не подключённой к проекту | T1 |
| Android Code Search (`cs.android.com`) | AOSP и androidx по веткам и версиям, плюс внутренние usages platform-API | T1/T2 |
| Репо библиотеки (raw-файлы, теги релизов) | сорсы, тесты и сэмплы, когда source jar не публикуется | T1/T2 |

**Режим B — по всей вселенной OSS** (кто и как использует X, существует ли рабочий пример):

| Канал | Что даёт | Tier |
|---|---|---|
| GitHub code search (MCP `search_code`/`search_repositories`, fallback `WebSearch` c `site:github.com`) | usages символа по всему GitHub, фильтры по языку и пути | по репо-источнику |
| grep.app | быстрый regexp по популярным репо (`grep.app/api/search`) | по репо-источнику |
| Sourcegraph public | кросс-хостовый поиск, структурные запросы | по репо-источнику |
| Android Code Search | как AOSP и Jetpack сами используют API | T1/T2 |
| `searchcode.com` и агрегаторы | fallback, когда прямые каналы недоступны | T3/T4 |

- **Tier присваивается репозиторию-источнику, а не каналу.** В режиме B канал лишь транспорт:
  vendor-endorsed сэмпл → T1/T2, domain-OSS → T3, случайный репо → T4. Никогда не единственный
  источник для API truth.
- **Доступность каналов зависит от окружения** (`ksrc` требует локального Gradle cache, MCP могут
  быть не подключены, grep.app и Sourcegraph могут блокироваться сетевой политикой). Список — seed
  для обнаружения, недоступный класс фиксировать как явное ограничение.

## Обнаружение и multi-channel

Таблицы выше называют классы источников, а не гарантированный набор инструментов. Не предполагать,
что названный инструмент существует, и не останавливаться на первом. Дисциплина из трёх шагов:

1. **Обнаружение** — инвентаризировать доступное сейчас: подключённые MCP-серверы и deferred tools
   через `ToolSearch`, плюс встроенные search/fetch. Gather-агент проводит обнаружение сам,
   оркестратор не предбиндит набор инструментов.
2. **Все релевантные каналы параллельно** — для класса вопроса запрашивать каждый обслуживающий
   его канал, а не один. Ширина охвата и есть цель.
3. **Cross-check и тиеринг** — верифицировать по ≥2 каналам, ранжировать по доверию, расхождения
   версий показывать явно, не выбирать молча.

Целый класс каналов недоступен — указать это как явное ограничение в выводе, чтобы сниженная
уверенность была видимой. Gather-агент перечисляет, какие каналы использовал и какие были недоступны.

## Context7

1. `resolve-library-id` по имени библиотеки и вопросу — кроме случая, когда дан точный `/org/project`.
2. Выбрать совпадение по точности имени, релевантности описания, числу сниппетов, репутации и
   benchmark score. Не туда — переформулировать (`next.js`, не `nextjs`) либо взять версионный ID.
3. `query-docs` с выбранным ID и полным вопросом пользователя, не одним словом.

Один провал `resolve-library-id` — стоп, не гнаться за синонимами.

## Оценка доверия

Источник может быть формально primary, а содержимое — устаревшим, для другой версии или
галлюцинацией. Оценивать tier до того, как поверить.

| Tier | Что | Источники |
|---|---|---|
| **T1** ground truth | артефакт без интерпретации | `ksrc`, код проекта, official release artifact |
| **T2** official docs | вендорская документация, releases, changelogs | `android docs`, Context7 для официальных либ |
| **T3** aggregated/AI | может галлюцинировать | Context7 для community-либ без вендорской docs |
| **T4** random web | блоги, StackOverflow, туториалы | WebSearch, случайный WebFetch |

**Память — не tier.** `MEMORY.md`, recalled facts и существующий код проекта фиксируют то, что было
верно на момент записи. При пробеле или сомнении перепроверять по T1/T2. Память — указатель «где
смотреть», не факт.

**По умолчанию T1 + T2 параллельно** для любого Edit/Write с внешней библиотекой — базовый режим, а
не «при сомнении». T1-only допустим только с явным обоснованием: стабильная stdlib; уже виденный
символ на той же pinned-версии, подтверждённый `ksrc`; тривиальное использование (конструктор data
class, enum value, константа). «Кажется очевидным» обоснованием не является.

**Валидация:**
- Версия источника расходится с версией в проекте → не использовать без cross-check, отметить.
- T3/T4 старше года в evolving-стеке (Compose, Ktor, AGP, KMP, Hilt, kotlinx.*) — понизить вес.
- T3 никогда не единственный источник для сигнатур и версий.
- Понизить tier на 1: источник не указывает версию; сигнатура не воспроизводится в `ksrc`; текст
  выглядит сгенерированным; туториал без даты.

**Конфликты:** T1 vs T2 — следовать T1, отметить расхождение, при существенном gap предложить bump.
T1/T2 vs T3/T4 — T1/T2 выигрывают безусловно. Два официальных расходятся — свежий changelog важнее
старой docs-страницы; непонятно — поднять вопрос, не выбирать молча.
