# Автономия слияния PR/MR

Дополнение к [[github-ops]] (механика) и скиллу `drive-to-merge`. Задача — довести PR до слияния,
не зависнув в ожидании.

## 1. Делегировать ожидание платформе — предпочтительно

Вместо поллинга CI поставить PR в auto-merge и переключиться на другую задачу; платформа сольёт,
как только проверки пройдут и ревью одобрено:

- GitHub: `gh pr merge <PR> --auto --squash` (требует включённого auto-merge и branch protection).
- GitLab: `glab mr merge <IID> --when-pipeline-succeeds` (учитывает merge train).

Разрешено ли это — решает политика проекта, см. ниже.

## 2. Если ждать всё же нужно — ждать неблокирующе

Опросить один раз `gh pr view --json statusCheckRollup,reviewDecision,mergeable,mergeStateStatus,isDraft,state`
→ классифицировать → `ScheduleWakeup`. Дисциплина cache-window: ≤270 с либо ≥600 с, избегать
280–550 с. Ограничить число последовательных опросов без изменений и сообщить о блокере вместо
бесконечного цикла.

## Политика проекта — читать, а не хардкодить

Автономность не одинакова во всех репо. Читать политику из `<repo>/CLAUDE.md`; при отсутствии —
вывести из профиля и явно назвать допущение.

| | Личный GitHub (свободный) | Командное репо (осторожный) |
|---|---|---|
| Нативный auto-merge | разрешён по умолчанию | **только с явного согласия** — молчаливый merge-train блокирует очередь команды |
| Gate `--auto` за раунд | включён | выключен, ручное ревью каждого раунда |
| Ручной merge gate | можно ослабить | **обязателен** |
| Pre-push checks | лёгкие | полный локальный `/check` перед каждым пушем |
| `--force-with-lease` | нормально | осторожно: сбрасывает чужие одобрения, ревью запросить заново |
| Параллелизм | агрессивный | консервативный, уважать merge queue |

По умолчанию для неличного или незнакомого репо — осторожный профиль. Неясно, какой применяется —
спросить один раз и зафиксировать ответ в `CLAUDE.md` репо.

## Предлагать автономность заранее

Обнаружив долгое ожидание впереди (CI ≥ 5 мин или ревью в очереди), проактивно предложить
автономный путь — «поставить auto-merge и переключиться на другую задачу?» — вместо молчаливого
зависания.

## Параллельная работа по нескольким PR

- Один worktree на PR (`Agent(isolation: worktree)`) — параллельные правки без конфликтов по диску.
- Долгий кросс-сессионный присмотр за многими PR — `/schedule` (cron routine).
- При включённом auto-merge присмотр в основном не нужен: платформа завершит каждый PR сама.
