# Логирование

Правило про исходный код приложений и библиотек. Не применяется к build-скриптам, shell-скриптам и
одноразовым CLI-скриптам, где печать в stdout и есть пользовательский вывод: запрет на прямую печать
нацелен на диагностику внутри переиспользуемого кода.

Всё логирование идёт через логгер, который проект уже использует: сначала обнаружить его
(зависимости, существующие вызовы, `CLAUDE.md` проекта), затем следовать. Логгера нет вообще —
предложить на этапе планирования, не выбирать молча.

## Постоянные логи — писать щедро

Логи не «шум, который нужно минимизировать», а актив для отладки. Хорошие цели: границы систем
(HTTP, БД, IPC, file I/O); ошибки с полным контекстом; ключевые смены состояний (auth, сессия,
lifecycle экрана, оценка feature flag); точки ветвления по неочевидным условиям.

Безопасно это ровно настолько, насколько release-сборка отсекает отладочные уровни: минификатор
вырезает вызовы, либо логгер фильтрует их по production-уровню. Добавляя тяжёлое
`debug`-логирование, убедиться, что механизм отсечения в проекте действительно есть; нет — оформить
отдельным решением, а не заливать production выводом молча.

## Временные логи — `// TEMP-LOG`

При расследовании бага инструментировать код логами — первоклассный инструмент, а не workaround.
После второй провалившейся гипотезы «по чтению кода» инструментирование обычно быстрее догадок.

**Маркировка.** Каждая временная строка получает комментарий `// TEMP-LOG` строкой выше (`#` или
`/* */` по языку) — одна grep-цель, независимая от языка, переживающая реформатирование.

**Продвижение — осознанное решение.** Строка действительно ценна в production — убрать маркер,
поправить уровень и обращаться с ней как с постоянным логом. «Забыть убрать» маркер нельзя.

**Gate финализации.** Перед `/acceptance` и открытием PR просканировать diff на `TEMP-LOG`;
любое совпадение блокирует gate: либо удалить, либо осознанно продвинуть. Секреты и PII в строках
`// TEMP-LOG` исключением не являются: diff проходит ревью, и «я бы его убрал» не защита.
