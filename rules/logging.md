# Логирование

Правило про исходный код приложений и библиотек. Не применяется к build-скриптам в декларативном
использовании, shell-скриптам (`echo`/`printf` — нативный вывод), одноразовым CLI-скриптам, где
`print` и есть пользовательский вывод, сгенерированному коду и тестовым фикстурам. Запрет на
`println` нацелен на диагностику внутри переиспользуемого кода, а не на вывод программы.

## Два режима

- **Постоянные логи** — часть продукта, идут в production, помогают отлаживать живые инциденты.
- **Временные диагностические** — добавляются при расследовании, удаляются до финализации.

Оба разрешены. Запрещено ad-hoc `println`, `console.log`, `print()`, `System.out`, `NSLog`.

## Система логирования обязательна

Всё логирование идёт через тот логгер, который проект уже использует: сначала обнаружить его
(зависимости, существующие вызовы, `CLAUDE.md` проекта), затем следовать. **Никогда не навязывать
технологию, которую проект не использует.**

Выбор логгера — часть задачи, только если логгера нет вообще; тогда предложить на этапе
планирования, не выбирать молча. Стартовые дефолты для greenfield: Android — Timber или
`android.util.Log`; JVM/Kotlin server — `slf4j` с `KotlinLogging`; KMP — `co.touchlab.kermit`;
iOS — `os.Logger`; Node/TS — `pino`/`winston`, никогда `console.*`; Python — stdlib `logging`;
Go — `slog`/`zap`, никогда `fmt.Println`; Rust — `tracing`/`log`, никогда `println!`.

Пользовательский вывод CLI логированием не является и от правил освобождён.

## Постоянные логи — писать щедро

Логи не «шум, который нужно минимизировать», а актив для отладки. Хорошие цели: вход и выход на
границах систем (HTTP, БД, IPC, file I/O); ошибки с полным контекстом (что пытались, с какими
данными, что стало причиной); ключевые смены состояний (auth, сессия, lifecycle экрана, оценка
feature flag); точки ветвления по неочевидным условиям.

Стриппинг в release — часть того, почему это безопасно: R8/ProGuard удаляет `Log.v`/`Log.d` при
стандартном блоке `-assumenosideeffects`; server-приложения ставят production level `info`/`warn`;
iOS `os.Logger` фильтрует `debug` сам. Добавляя тяжёлое `debug`-логирование, проверить, что механизм
стриппинга есть; нет — оформить отдельным решением, а не заливать production выводом молча.

Уровни — стандартная серьёзность, соглашения проекта побеждают: `error` — операция провалилась,
всегда с причиной; `warn` — деградация, fallback, исчерпаны повторы; `info` — значимые
lifecycle-события, один на событие, не на итерацию; `debug` — внутреннее состояние для
расследования; `trace` — детали за итерацию, raw payload. Выбирать по принципу «кому это нужно
видеть и когда», а не по тому, насколько лог интересен в момент написания.

## Временные логи — `// TEMP-LOG`

При расследовании бага инструментировать код логами — это первоклассный инструмент, а не
workaround. После второй провалившейся гипотезы «по чтению кода» инструментирование обычно быстрее
дальнейших догадок.

**Маркировка.** Каждая временная строка получает комментарий `// TEMP-LOG` строкой выше (`#` или
`/* */` по языку) — одна grep-цель, независимая от языка, переживающая реформатирование.

```kotlin
// TEMP-LOG: investigating null state on checkout
Timber.d("order=%s, cart=%s", order, cart)
```

**Цикл:** добавить → воспроизвести → прочитать вывод → гипотеза → итерировать. Как только
первопричина понята и фикс на месте — удалить все строки `// TEMP-LOG`.

**Продвижение — осознанное решение.** Строка действительно ценна в production — убрать маркер,
поправить уровень и обращаться с ней как с постоянным логом. «Забыть убрать» маркер нельзя.

**Gate финализации.** Перед `/finalize`, `/check` и открытием PR просканировать diff:

```
git diff | grep -nE 'TEMP-LOG'
rg -n 'TEMP-LOG' --no-heading
```

Любое совпадение блокирует gate: либо удалить, либо осознанно продвинуть.

## Что никогда не идёт в лог

Независимо от режима: секреты (пароли, API-ключи, токены, session cookies, signing keys); PII без
необходимости (полные имена, email, телефоны, адреса, ID документов — при крайней нужде стабильный
хэш или последние 4 цифры); платёжные данные (полный PAN, CVV, IBAN); большие блобы по умолчанию —
обрезать с явным `…[N bytes truncated]`; всё, что попадает под GDPR, HIPAA или PCI без явного
разрешения.

Строки `// TEMP-LOG` исключением не являются: diff проходит ревью, и «я бы его убрал» не защита.

## Когда инструментировать

1. Пишешь новый код с нетривиальным потоком → постоянные логи на границах и ключевых переходах по
   ходу, не отдельным шагом.
2. Воспроизводимый баг, чтение кода не сходится → `// TEMP-LOG`. Не угадывать дальше после двух
   провалившихся гипотез.
3. Нестабильность или плавающая проблема → `// TEMP-LOG` в подозрительных точках гонки, часто на
   `trace`. Потребует нескольких итераций.
4. Ревью нашло неясный runtime-путь → постоянный `debug`-лог на этом пути, а не комментарий,
   объясняющий, что делает код.
